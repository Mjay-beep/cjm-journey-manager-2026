## 0. 선결: 구조적 이슈 (반영 전 정리해야 다른 요청들이 깔끔히 들어감)

### ISSUE-A. `ord_acc` 분할 — 액세서리 주문과 오프라인(대리점/고객센터) 통합 개통이 한 L2에 섞임
- 현재 `ord_acc`는 두 가지 L2명을 동시에 가지고 있음(데이터 정합성 깨짐):
  - "액세서리 주문"
  - "[대리점/고객센터] 구매/개통"
- 산하 L3가 9개인데, **순수 액세서리 주문은 `ord_acc_order` 한 개**, 나머지 8개(`ord_phone_offline`, `ord_offline_form`, `ord_offline_apply`, `ord_offline_setup`, `ord_net_offline`, `ord_combo_offline`)는 **대리점/고객센터 통합 개통 여정**.
- **제안 (반영 시):**
  - `ord_acc`는 액세서리 주문 단일 의미로 축소(L3 `ord_acc_order`만 유지).
  - 대리점/고객센터 통합 개통을 **신규 L2** `ord_offline` 같은 새 코드로 분리(이름 예: "(대리점/고객센터) 통합 개통").
  - 산하 L3 7개를 그쪽으로 이관.
- 이걸 먼저 정리하면 REQ_007 / REQ_008 / REQ_009 / REQ_010 / REQ_011이 자연스럽게 들어감.

### ISSUE-B. L3 코드 prefix가 부모 L2와 일치하지 않는 케이스
- 예: `ord_acc` 산하에 `ord_phone_offline`, `ord_offline_form`, `ord_combo_offline`, `ord_net_offline` 등 다른 prefix가 섞임.
- 예: `expl_prsnl` 산하 L3 `expl_plan_theme` (요금제 prefix지만 개인화 추천에 위치).
- 예: `use_cs` 산하 `use_cs_email` L4가 `ent_chat_email_01`, `ent_chat_bot_01` 등 다른 도메인 L4 코드 참조.
- 예: `use_pay_*` L3가 `use_bill` 산하에 있음 — bill / pay 두 prefix가 한 L2에 공존.
- 예: `exp_net` 산하 L3가 `ord_net_*` prefix.
- **제안:** 본 검토 적용 시 *함께* 일괄 정합화. 코드 prefix = 부모 L2 코드 prefix 원칙 수립.

### ISSUE-C. 동일 L4 코드 재사용 (cross-reference)
- `cmn_auth_01 | 본인확인` 코드를 `ent_store_consult` 산하에 사용 → REQ_005에서 강희정님이 정확히 지적("인입 단계에 본인확인이 있어 구매단계 본인확인과 혼동").
- `cmn_` prefix는 "공통" 의도로 보이나, 실제로는 위치별 의미가 달라야 함.
- **제안:** 공통 코드 재사용 정책 결정 필요(같은 활동이라도 위치별로 별도 L4 부여 권장).

### REQ_007 | `ord_acc` 액세서리 주문 안에 대리점 개통 — 강희정

- **판정: ✅ 수용 (ISSUE-A로 흡수)**
- 처리: L2 `ord_offline | (대리점/고객센터) 통합 개통` 신설로 분리. 단, 강희정님 추가 지적("고객센터=TDS 전담 채널, 유통망과 다른 그룹")은 정책 결정 필요 — 본 CJM에서 두 채널을 통합 L2로 두되 channels 태그로 구분할지, L3 레벨에서 대리점/고객센터를 또 분리할지.

### REQ_008 | `ord_offline_form` → "원스톱 개통 진행"으로 명칭 수정 — 강희정
- 요청: "플래너 상담 후 원스톱 개통 또는 신청서 작성으로 분기"
- **판정: ⚠️ 조건부 수용**
- 근거: 현재 `ord_offline_form` ("주문 진행 (대리점-스마트플래너)")과 `ord_offline_apply` ("신청서 작성")가 별도 L3로 존재. 이름 변경 자체보다는 **두 L3의 분기 관계를 명확히** 하는 게 우선. "원스톱 개통"이라는 표현이 채널 내부 용어라면 도메인 표준 용어 확인 필요.
- 결정 사항: 명칭 변경 전 강희정님과 1차 합의(스마트플래너 통합 흐름 vs 원스톱 흐름 vs 신청서 흐름의 구분).

### REQ_009 | `ord_combo_offline` L4 정리 — 강희정
- 요청: "swing 화면 순서와 고객센터 전용 기능이 혼재. 신청서 작성 / 구비서류 제출 / 결합가입 완료 MMS 수신으로만 구성"
- **판정: ⚠️ 조건부 수용**
- 근거: 현재 L4가 8개로 매우 세분화(나혼자/가족 결합, 가족 회선 추가, 동의, 할인 확인 등). 강희정님 제안대로 3개로 축약하면 정보 손실. 다만 "신청서 작성 → 구비서류 제출 → 완료 MMS" 흐름을 **표준 L4**로, 나머지는 분기 표시(예: 가족결합 시 추가)로 재정렬 권장.
- 결정 사항: L4 통합 vs 세분화 정책.

### REQ_010 | `ord_combo_offline`이 왜 `ord_acc` 하위? — 강희정
- 요청 (질문): "L2 결합상품가입은 온라인 채널 기준? 결합 신청이 왜 L2 액세서리 주문의 L3?"
- **판정: ✅ 수용 (ISSUE-A로 흡수, 답변 필요)**
- 답변: L2 `ord_combo | 결합 상품 가입`이 별도로 존재하며, `ord_combo_offline`이 액세서리 L2에 들어간 건 구조 오류. ISSUE-A 정리 시 신설 `ord_offline`으로 이관하거나 `ord_combo` 산하로 재배치 권장.

### REQ_025 | `ord_phone_order` 디바이스 주문 — 정희정 (질문)
- 요청 (질문): "디바이스 주문 프로세스 중 배송만 별도 L3, 각 프로세스(가입 유형)는 주문서 작성 L3로 분리된 이유?"
- **판정: ❓ 요청자 회신 필요**
- 답변 후보: 현재 `ord_phone_order`는 단말 옵션·배송, `ord_phone_form`은 가입 정보·요금제·할인. 사용자 흐름상 분리가 합리적이지만 명명이 모호. "디바이스 선택" / "가입 조건 선택"으로 리네임 검토.

### REQ_026 | 주문서 작성 vs 신청서 작성 — 정희정 (질문)
- 요청 (질문): "주문서 작성과 신청서 작성의 차이?"
- **판정: ❓ 요청자 회신 필요**
- 답변: 주문서(`ord_phone_form`)=가입 조건·할인 선택, 신청서(`ord_phone_apply`)=본인인증·약관·결제. 명칭이 혼동 유발. "가입 조건 입력" / "본인인증 및 약관 동의"로 리네임 검토.

### REQ_046 | `use_cs_offline` 상태 분리 — 유수빈
- 요청: "상담 발생(인입) / 진행(처리중) / 완료 분리. 미결 건 누수 방지, 미결 고객 OB 마케팅 지양"
- **판정: ⚠️ 조건부 수용**
- 근거: CJM은 본래 액티비티(고객 행동) 단위. "상태"는 액티비티가 아니라 케이스 라이프사이클 속성. CJM L4에 상태 자체를 박는 것보다는 별도 **status 필드/태그**를 갖는 게 데이터 모델상 깔끔.
- 결정 사항: 상태를 L4로 추가할지 / 별도 태그로 둘지 결정. 후자가 본 모델 일관성에 맞음.
